# LongClaw 0.3.1

0.3.0's update could be found and downloaded but not installed: *Restart to
update* answered *The download didn't finish*, and *Try Again* did nothing. The
download was fine. The archive it arrived in was not, and this release replaces
it with one that installs — along with three faults in the pane that the first
one had been hiding.

Nothing else changes. If you installed 0.3.0 from the DMG and never pressed
*Update*, this release adds no feature you are missing.

**[How to use it](../user-guide.md)** — project folders, the file format,
backups, agent setup, and recovery.

## Requirements

- macOS 13 or later.
- Apple Silicon. `LongClaw_0.3.1_aarch64.dmg` is an Apple Silicon build; there
  is no Intel or universal binary in this release.

## Updating from 0.3.0

*Settings → Updates* will offer this release, and `Update` then `Restart to
update` installs it. **This works from the 0.3.0 you already have** — the
defect was in the file 0.3.0 was being handed, not in the copy doing the
handing, so no reinstall is needed to escape it.

If 0.3.0's update left the pane sitting on *The download didn't finish*,
pressing `Update` again is enough. Nothing was left behind: the failed install
never reached your installed copy — it stopped while unpacking into a temporary
directory of its own, which it then removed.

**From 0.2.0** the same two presses apply, and they always did — 0.2.0's own
update path is unaffected by any of this.

**From 0.1.0** it is a download: open the `.dmg` and drag LongClaw into
Applications, replacing the copy that is there. Your projects are files in
folders you chose and the app does not hold them, so there is nothing to
migrate.

## The update that could not install

macOS writes a file's extended attributes into a sibling file when it packs one
— `._LongClaw.app` beside `LongClaw.app` — and Apple's own `tar` folds those
siblings back out of sight when it reads. 0.3.0's update archive was packed and
inspected with that `tar`, so it listed eleven clean entries. It held
twenty-two.

The updater does not use Apple's `tar`. It saw the siblings as ordinary files,
and it strips the leading component of every path it extracts, so the
single-component `._LongClaw.app` became an empty path and the first entry in
the archive was written over the directory the update was being unpacked into.
Every install failed, on every machine, on entry one.

0.3.1's archive is packed with that behaviour switched off. More to the point,
**the release now reads its own archive back** before it will publish it,
walking the file the way the updater walks it rather than the way macOS reads
it, and refuses to ship one carrying those siblings or anything but LongClaw at
its root. The check that would have caught this now runs on every release, and
runs again in the repository's own test gate.

## Three faults behind it

A first defect that breaks something completely hides the ones after it. All
three are in this release.

- ***Try Again* now tries again.** The downloaded bytes were discarded the
  moment an install was attempted, so after a failure there was nothing left to
  retry and the button did nothing at all. The bytes are now kept until an
  install succeeds. The same download is reused; nothing is fetched twice.
- **A failed install no longer blames the download.** Every way an install could
  fail reported *The download didn't finish* — which is how LC-265y's first
  hours went to the network, a file that had already arrived and verified. An
  install that fails now says so: *The update couldn't be installed.*
- **One definition of "the same release".** The pane's *ready to install* flag
  and the bytes it holds could disagree about which release they belonged to if
  a version was republished, leaving the pane offering to install something it
  no longer had. They now answer that question the same way.

## The download link in the pane

When the app cannot offer an update it points at the download page instead. It
named `longclaw.io/download`, which is not a page. It now names `longclaw.io`.

## The local-only boundary

Unchanged. This release adds no request, removes none, and touches nothing
about what is stored.

LongClaw works with no account and no sync. With no internet at all, every
feature behaves exactly the same — the only things that do not happen are the
update check and the star count.

- There is no sign-in, no cloud, no telemetry, and no crash reporting.
- Nothing about you, your projects or your tickets leaves your machine.
- The app makes the same two kinds of request 0.3.0 made, both to LongClaw's own
  repository: the update check described in [0.2.0's notes](v0.2.0.md), and a
  `GET` for the public star count, described in
  [0.3.0's](v0.3.0.md#what-the-star-request-is).
- **The same off switch covers both.** Turn automatic checks off in *Settings →
  Updates* and nothing is requested — the preference is read before the request,
  not after it.
- The only thing stored outside your project is the list of folders you have
  opened, their order, and the update preference and the date of the last
  successful check, in `~/Library/Application Support/io.longclaw.desktop/`.
- Local diagnostics go to stdout when you launch from a terminal with
  `LONGCLAW_LOCAL_DIAGNOSTIC=1`, and are never transmitted.

## What is not here

Unchanged from 0.3.0, and still separate phases rather than partial features.

- **Phase 2 — terminals.** Running commands inside the app is not in this
  release.
- **Phase 3 — sync and teams.** Multi-user projects, shared servers, accounts
  and billing are not in this release.

Also not in v0: Windows and Linux builds, custom themes, and hard ticket
deletion.

## Known limitations

Everything 0.3.0 listed still applies. One is about this release:

- **A failed install holds the download in memory until you quit**, because
  keeping the bytes is what makes *Try Again* possible. It is the file you can
  see the size of in this release's assets, and nothing is written to disk to
  hold it.
