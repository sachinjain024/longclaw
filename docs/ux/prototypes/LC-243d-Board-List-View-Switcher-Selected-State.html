How the view switcher says which half is pressed

PR #47 brought the Board | List segment to the prototype: the mark in front of each word, and the accent fill on the pressed half (prototype.css:334). The fill is the part being reconsidered — the ask is to take the background colour off and let the mark carry it. Only the mark carries it reads three ways, and this page is the three.

Try this

  • compare stacks today's control and all three answers in the header row they live in. Read down the left edge: the question is really "which of these four can you answer at a glance, without having first been told what the control does".
  • Flip board pressed / list pressed. Option C is the one to watch — the marks move rather than a colour moving.
  • Switch to dark. The fill was doing more work in dark than in light, so this is where removing it costs the most.
  • Try graphite. Its accent is a grey, which is the hardest case for A and B and no case at all for C.
  • states puts one option under your pointer and your Tab key. Hover each half and Tab into the group — hover and focus are real here, not simulated, because a prototype that draws its own :hover is a prototype that agrees with itself.
  • copy deck is the last scene. Option A is the only one that changes what the deck holds.

What each costs

  • A — the only one that is not CSS alone. ViewSegment drops the words, and the accessible name goes with them unless the buttons gain aria-label. Narrowest control of the four, by about 78px.
  • B — CSS only. Keeps the prototype's own layout exactly; only the fill's job moves to the ink.
  • C — CSS only, and ViewSegment does not change at all: it already draws both marks, so hiding one is the stylesheet's business.

All three delete a rule

PR #47 had to add a second focus ring for the pressed half, because --lc-accent-human-ring is the accent at 14% and over the accent fill it composited to that fill exactly — an invisible ring. With no fill under it the ordinary inset ring is legible on both halves again, and that special case deletes itself whichever option wins.

Open questions

  • Do the settings dialog's Appearance and Estimate segments follow? They share one rule with this control today, on purpose — that was the call taken in PR #47, and components.md:31 was amended to record it. Whichever option wins here either takes them with it or breaks that pairing, and breaking it means the shared rule goes back to prescribing something only one control uses. Not shown on this page; it wants its own look.
  • Is state-by-colour enough on its own? A carries an underline and B a 600 weight so that neither leans on hue alone (components.md:31: "none relies on color alone"). Both are proposals, not requirements — say the word and they come off, but C is then the only option that survives greyscale.
  • C leaves the unpressed word indented by the width of the mark it is not wearing. Reserved on purpose, so the group does not resize as you toggle it. The alternative is a control that changes width under the pointer. Which is worse?
  • A is 78px narrower. The header is the row that ran out of width at 200% zoom (a11y:audit A5), so this is a real gain — is it worth two unlabelled marks?
