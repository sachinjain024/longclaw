LC-249a · extends LC-233

Make installing the longclaw command explain itself

LC-233 put the command in the bundle and a button in two places. What it never did was say why. The pane opens on what the button writes to the filesystem and closes on a promise about folders — a complete answer to a question nobody asked before they knew what the thing was for.

Try this

  • The driver opens on first launch · absent. The dialog is three things now — the lede, the preview, the buttons. Everything that reported rather than argued moved to the pane.
  • Flip to dark in the driver and watch the preview block. It stays a terminal. In revision 1 it turned into a light-grey card — see below.
  • Press refuse the write, then Install. The dialog stays up, the refusal lands above the line to paste, and the primary becomes Try again — a button LC-233 never offered.
  • Switch to stale. This is the state that reads as "installed" from a terminal and runs the wrong build; note it is the one state where the preview block is a warning rather than an invitation.
  • Switch to dismissed. Today this path is silent — the dialog closes and nothing says the press was remembered.
  • copy deck is the last scene. Every string on every other scene is rendered from it.

What is new

  • A preview of the thing you are installing. One real command, its real output. This is the design's strongest idea and the one the shipped pane is most obviously missing.
  • Fewer sentences, everywhere. Both surfaces now make one argument and stop. The status line survives only where it is news, the what it writes box and the preflight line are gone, and so is the pane's closing note.
  • A dismissal that says so, with the way back in it.
  • An Ask again checkbox. commandLinePrompted is written once today and has no way back: skip on first launch and that Mac can never be asked again.
  • Buttons together, bottom-right. Today the primary sits mid-body in .cli-actions and the dismissal sits in the dialog's own footer, so the two halves of one decision are in two places.

Revision 4 — the dialog's copy, from the design

The title and lede are now the Claude Design project's, and the preview has its shape. Three edits were made on the way in, all of the same kind — the design says something the product does not do.

  • The lede's slips are repaired: "ito" → "to", and "So" → "so" mid-sentence. The sentence is otherwise the design's.
  • The command is longclaw ticket list, not longclaw list --status todo. That verb does not exist and it takes no --status. A block whose entire job is to be believed cannot open on a line that returns unknown command. If the filtered form is wanted, that is a CLI feature and a real ticket.
  • .tickets → .longclaw in the second output line. Same defect, smaller: naming a folder the app does not create.

The output is knowingly abbreviated — settled in review, and LC-249a's second checklist item is amended to match. ticket list prints pretty-printed JSON: on this repository, 251 objects of about fifteen fields each. There is no truthful two-line rendering of that, and revision 3's compacted one-line JSON was already a stylisation presented as a transcript — the worse of the two failures, because it looked literal and was not. The block is illustrative and says so in its caption.

Two honest alternatives were considered and are still available later without changing the dialog's shape: longclaw ticket list | jq -r '.[] | "\(.key) \(.title)"' prints exactly these two lines but is noisy for a first-run modal; and a human-readable list mode on the CLI would make the design's line true outright, which is a feature and its own ticket.

Revision 3 — from review

The pane came down to the same shape as the dialog: a name, one sentence, the preview, the action. Four things went.

  • The lede lost its second clause. "— the same files the board is showing you" explained the app to somebody already looking at it.
  • The pane lost the absent sentence. The dot and the Install button already said it. Every other state keeps its sentence, because in those it is news rather than restatement — most of all occupied and unavailable, where it is the only content there is.
  • The preflight line and the what it writes box are gone entirely, from both surfaces. This removes the only reason for the status-DTO change — nothing renders writability any more, so CommandLineStatus needs no new field and LC-249a's fifth checklist item is now dead. That is the one consequence of this round worth deciding rather than absorbing.
  • The pane lost its closing note. LC-233 put it there on purpose: the pane sits in project settings and is not project data, the same exception the Theme pane makes for the appearance (D-42), and screen-specs.md:334 was amended in place to say so. Nothing on screen says it now — see the seventh open question.

Revision 2 — from review

  • The dialog lost its status line and preflight row. On the two states the offer actually opens on, "longclaw is not on your PATH yet" is the dialog restating why it is open, and the preflight reassured about a problem the reader did not yet know they might have. Both stay in the pane.
  • The dialog lost the what it writes box. It answered a question that gets asked one screen later. The pane keeps it — see the sixth open question, because this is the consent detail and moving it out of the consent moment is not obviously right.
  • The dialog is wider — 560px against .confirm-dialog's min(420px, 92vw), as a .wide modifier so the delete confirmations stay narrow.
  • The dark-mode preview is fixed, and it was a real defect. Revision 1 used --lc-inverse-surface, which does not mean "the dark one" — it means the inverse of the current theme (#171923 light, #e9eaf2 dark). So the terminal became a light-grey card exactly when the app went dark. It now sits on --lc-tile, near-black in both appearances and already the app's own terminal surface for the agent actor tile (styles.css:4070). The ink had the identical trap and is pinned to the dark ramp both ways.

Where the design is wrong

Four things in CLI Install.dc.html cannot ship as drawn. The prototype corrects them rather than transcribing them.

  • The path. The design links Contents/Resources/bin/longclaw. It is Contents/MacOS/longclaw — a Mach-O under Resources is the classic notarization rejection, which LC-233 names outright.
  • The admin prompt. The design has an auth stage — "macOS is asking you to approve the change". There is no such stage and there cannot be: release-audit.mjs:254 fails the build on Command::new, so osascript … with administrator privileges is unavailable and no privileged helper was built. The write is a synchronous symlink that succeeds or returns EACCES.
  • The commands. The design's terminal shows longclaw list --status todo printing a formatted table, and longclaw --version. The verb is ticket list, it takes no --status, it prints JSON, and there is no --version at all. A trust-building block that shows a command which does not exist inverts on first use.
  • Four states, not five. The design covers ask / installing / done / error. The app has linked, stale, occupied, absent and unavailable, and stale is the interesting one.

Settled before drawing

  • UI pass only. No Remove link, no --version badge, no Reveal in Finder, no status-bar chip. Each is new capability, and LC-233 declined the first two on purpose.
  • The pane stays in project settings. The design puts it in an app-level Settings window under Integrations; no such window exists, and building one is its own ticket. The row treatment comes across, the re-home does not.
  • Dismissal is per-Mac, not per-project. The design says "permanent for this project" in one place and "when I open a project" in another. commandLinePrompted is a device preference, and it is right: the link is a fact about the Mac.

Settled at implementation

  • The preview stays in the dialog. The dialog is where the decision is actually made, so the argument has to be in it.
  • The human accent wins, on both surfaces. The check on the answered title and the pane’s linked dot are the human accent, and .cli-state.ok moved to it: LC-233’s comment argued green as “a machine is involved and it is working”, which is true of what the command does and is the wrong subject — the sentence reports that somebody pressed a button. One installed state cannot be two colours on two surfaces.
  • Ask again belongs to the pane. Offering somebody the chance to opt out of being asked while they are being asked is one more control in a first-run modal for a decision they have already been handed.
  • stale keeps its sentence in the dialog. It is the one state whose sentence nothing else on that screen carries.

Open — decide these

  • Is the preview worth its height in the dialog? It is four lines in a modal a person meets before they have made a ticket. The alternative is preview in the pane only, and a one-line lede in the dialog. The dialog is where the decision is actually made, which argues for keeping it.
  • Human accent or agent accent for success? The design is explicit — "installing is a human act, so its confirmation stays in the human accent". .cli-state.ok ships the agent accent today, with a comment arguing the opposite. Both arguments are good; this prototype draws the design's. One of the two comments has to go.
  • Does Ask again belong to the offer or to the pane? Drawn in the pane. Putting it in the dialog as well would let a person opt out of being asked at the moment they are being asked, which is tidier logic and one more control in a first-run modal.
  • The lede names PATH but not the write. Revision 4 improved this — "Add the longclaw binary to your PATH" at least says something lands somewhere. It still does not say where: no /usr/local/bin, no symlink, and that path now appears only in the sudo line after a refusal. This is the one press in the app that writes outside a project folder, and LC-233's stated reason for prompting at all was that it must never do so silently. Is naming PATH enough?
  • Nothing says the pane is not project data. It sits in the project settings panel next to labels and statuses, which are all stored in longclaw.yaml, and now reads exactly like one more of them. The nav does not say otherwise. If the closing note is not coming back, something else has to carry it.

What this asks of the code

  • Nothing is needed from Rust. Revision 3 removed the preflight, which was the only reader of the proposed writability field, so CommandLineStatus is untouched and all five states are already answered. This is now a frontend-only change.
  • devicePreferences.ts needs commandLinePrompted to be clearable; rememberCommandLinePrompted only ever sets it.
  • The preview's command and output are a constant beside COMMAND_NAME, not copy in the pane — a demo of the CLI that lives in the frontend is a demo that goes stale the first time the CLI changes and nothing fails.
  • ConfirmDialog.tsx takes no className, so the .wide modifier needs one — or a width prop. Do not widen .confirm-dialog itself: the delete confirmations are two sentences and should stay narrow.
  • --lc-tile is the terminal surface, not --lc-inverse-surface. The second is the inverse of the current theme and flips; the first is near-black in both. Worth a comment where it is used, because the names do not say which is which.
  • a11y:audit is in scope: this touches a modal, and the button order inside it changes.
